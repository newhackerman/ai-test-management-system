# QA 自动化 Skills 使用指南

本目录把 AI 测试管理系统项目里沉淀的自动化测试方法做成了 5 个分步 skill，外加一个通用测试框架模板。给一个仓库地址或一份代码，就能按顺序自动完成部署、分析、用例生成、执行、修复、提交全套测试工作。

## 流水线

```text
仓库地址 / 本地代码
  └─► qa-deploy    部署：拉代码、认技术栈、拉起服务、加自愈
        └─► qa-casegen   分析：AI 读接口，生成分类用例
              └─► qa-execute   执行：跑测试、分流失败、写报告
                    └─► qa-fix       修复：按优先级修、干净库回归（需用户确认修哪些）
                          └─► qa-submit    提交：分支、推送、提 PR（需用户确认提交内容）
```

每一步的输出就是下一步的输入。用户只需要在开头给仓库地址或代码路径，中间不需要再给材料。

## 五个 skill

| Skill | 做什么 | 输入 | 输出 |
| --- | --- | --- | --- |
| `qa-deploy` | 拉取仓库、识别技术栈、启动依赖与前后端、健康检查、写 `ops/` 自愈脚本与看护任务 | 仓库地址或本地代码路径 | 跑起来的部署 + 部署说明（技术栈、端口、基准提交、测试账号位置、健康检查地址） |
| `qa-casegen` | AI 分析接口（OpenAPI、路由、数据模型），按冒烟、鉴权、CRUD、校验、边界、安全、E2E 生成用例 | 部署说明 + 跑起来的服务 | `qa-automation/` 框架 + 用例 + 用例清单 |
| `qa-execute` | 按冒烟、API、E2E 顺序执行，分清测试 bug 与真实缺陷，写 Markdown 报告 | 框架 + 用例清单 | `reports/TEST_REPORT.md` + 按优先级排好的缺陷清单 |
| `qa-fix` | 按优先级修缺陷，修完在干净库上全量回归，更新报告。开始修之前先让用户确认修哪些：全部、只修高优先级、还是不修只出报告 | 缺陷清单 + 报告 | 修好的代码 + 更新后的报告 |
| `qa-submit` | 建分支、按逻辑分块提交、推送、检查无重复 PR 后提 PR。提交之前先把分支名、文件、提交计划和 PR 草稿给用户确认 | 干净的树 + 全绿的回归 + 报告 | 分支、提交记录、PR 链接 |

## 模板

`template/` 是从本项目 `qa-automation/` 抽出的通用骨架：配置、HTTP 客户端、断言、fixtures、数据工厂、报告生成器、E2E 脚手架、冒烟测试。`qa-casegen` 会把它复制到目标仓库里做 `qa-automation/`，再按目标项目适配。模板自带 `README.md`，里面有五步适配法：改环境变量、对齐登录与返回结构、按实体加数据工厂与 fixture、按模块写用例、跑测试出报告。

## 在 Muse 里使用

- 把 `qa-deploy`、`qa-casegen`、`qa-execute`、`qa-fix`、`qa-submit` 这五个目录复制到 `~/workspace/custom-skills/` 下，Muse 就能按名字调用它们。
- 直接说“给这个仓库做全套测试：<仓库地址>”，Muse 会按顺序跑完五步。
- 也可以只跑某一步，比如“只帮我生成用例”或“只跑测试出报告”。

## 不用 Muse 时手动使用

- 按顺序读每个 skill 目录下的 `SKILL.md`，照里面的步骤做。
- 模板在 `template/`，按它 `README.md` 的五步适配法改到目标项目上。

## 约定

- 绝不使用、导入或复制目标仓库自带的测试框架与测试代码，只读它了解已有覆盖。
- 每个用例数据用唯一名字，清理是尽力而为，残留数据不影响其他用例。
- 只有在干净库上的最终回归全绿，才可以报 100% 通过。
- 提 PR 是对外操作，换个新项目要先经用户点头再提。
- `qa-fix` 与 `qa-submit` 是需要用户确认的步骤：修代码会改产品，提交会动远程仓库；测试人员有时只需要报告，不修代码。只说“做测试”不等于同意修，也不等于同意提交。
- 密码、token、密钥不进 skill、不进模板、不进提交。
